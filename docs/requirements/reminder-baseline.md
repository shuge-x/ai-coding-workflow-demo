# Story 02 到期提醒候选需求基线

状态：教学示例，尚未获得真实用户确认。以下对话和候选规则由课程作者编写，用于演示访谈方法；不是本次会话用户的回答，也不是项目已批准需求。实际跟做时，请记录你自己的回答和来源。

## 问题与目标

原始表达是“任务快到期时，系统能提醒相关人员”。本轮要明确提醒对象、时间语义、渠道、生命周期与失败处理，留下可审核的规则与未决项。

## 代码事实

事实与出处见 [起始代码核对](reminder-code-facts.md)。当前起点的任务具有可选截止日期；没有可直接复用的负责人、用户身份或收件人关系。

## 作者设定的候选规则

| 编号 | 候选规则 | 来源与状态 |
|---|---|---|
| D01 | 提醒面向主动订阅某任务的个人 | 教学示例第 1 轮；真实用户待确认 |
| D02 | 截止日前一次提醒，逾期催办另议 | 教学示例第 2 轮；真实用户待确认 |
| D03 | 按收件人时区，在任务日历截止日前一天 09:00 提醒；缺失时区需补充 | 教学示例第 3 轮；真实用户待确认 |
| D04 | 完成、删除、取消订阅会取消未发送提醒；改期重算未发送计划 | 教学示例第 4 轮；真实用户待确认 |
| D05 | 无截止日期不排程；新建或改期后提醒时刻已过则跳过 | 教学示例第 5 轮；真实用户待确认 |
| D06 | 邮件仅为候选渠道 | 教学示例第 6 轮；真实用户待确认 |
| D07 | 可以取消某任务的提醒订阅 | 教学示例第 7 轮；真实用户待确认 |
| D08 | 不无限重试；投递与阅读分别描述 | 教学示例第 8 轮；真实用户待确认 |

## 真实用户确认

尚未收集真实用户的逐条确认。D01–D08 均不得标为项目已批准规则。

## 待决策与后续访谈

1. 谁能建立订阅，收件人身份和邮箱如何验证？
2. 时区变更、夏令时异常，以及实际截止日期的业务解释如何处理？
3. 已发送后再改截止日期，是否允许另一次提醒？
4. 全局免打扰如何覆盖任务级安排？
5. 重试上限、间隔、成功判定和最终失败反馈是什么？

这些问题仍可能改变设计；后续不能把本记录直接当成可实施 Spec。

## 情景检查 也是候选规则的推演

- 若截止日为某月 20 日，且采用 D03，则候选提醒时刻为收件人所选时区 19 日 09:00；这不是从数据库里的中午时间推得的要求。
- 若任务在发送前完成，按 D04 取消待发送计划；当前 seed 中“已完成且日期在过去”的任务可用来追问这条规则。
- 若新任务的候选提醒时刻已经过去，按 D05 跳过；不能默默切换成补发策略。
- 若发送服务接受请求，也不能据此声称用户已阅读；成功条件仍需确认。
